# 会话删除插件 —— 功能规格说明书

> 插件包名：`dsh-session-trash`
> 目标产品：DeepSeek Harness (DSH) Web GUI
> 适用版本：DSH `>= 0.2.0-rc.1`（实测 `0.2.0-rc.2`，profile `desktop`）
> 文档状态：与 `v1.4.0` 代码一致

本文档是第一阶段（需求分析与技术方案设计）的交付物。所有条目都标注了实现状态，未实现的部分明确列为「范围外」，不做模糊承诺。

---

## 1. 背景与问题定义

### 1.1 现状

DSH 侧栏的「会话设置」菜单（截图中的右键/更多菜单）当前只有四个操作：

| 现有操作 | 菜单 id | order | 语义 |
|---|---|---|---|
| 置顶会话 / 取消置顶 | `pin` | 100 | 调整排序，可撤销 |
| 重命名 | `rename` | 200 | 修改标题 |
| 分叉会话 | `fork` | 300 | 复制到新会话 |
| 归档会话 / 取消归档 | `archive` | 400 | 隐藏但保留全部数据，可取消归档 |

**没有任何删除入口。** 这不是 UI 遗漏，而是产品当前的能力边界，已通过源码核对确认（见 `ARCHITECTURE.md` §2）：

1. 会话持久化接缝 `ctx.sessionPersistence` 的契约只有 `create` / `open` / `stat` / `list` / `flush` 五个方法，**没有** delete / remove / purge。
2. 会话控制器的客户端 Remote 命名空间只有 `create` / `fork` / `rename` / `list` / `projections` / `history`，**没有** delete。
3. 全量检索提取出的 DSH 产品包（327 个 `@deepseek-ai/*` 包）中，不存在任何删除已存储会话的实现。归档（`archiveSession`）是唯一的「隐藏」手段。

因此「删除」必须由插件自带宿主端能力，不能依赖既有 API。

### 1.2 用户痛点

- 会话列表只能增长。归档会把它移出默认视图，但数据仍在磁盘上，且归档列表本身也在增长。
- 无法清理实验性、一次性、已无价值的会话及其磁盘占用（单个会话日志实测可达数百 KB 到数 MB）。
- 涉及敏感内容的会话无法真正移除，只能归档隐藏——这不满足数据删除要求。

### 1.3 目标

在**不修改 DSH 源码**的前提下，为会话提供安全、可恢复、可审计的删除能力。

## 2. 功能需求

### FR-1 单会话删除（菜单入口）✅ 已实现

- **FR-1.1** 在 `sidebar.workspaces.session.menu.item` 槽位新增「删除会话」行，`order = 500`，排在归档（400）之后，使破坏性操作位于菜单末尾。
- **FR-1.2** 使用组件库的 `MenuItemButton`，`danger = true`，图标 `IconTrashOutlineRegular`，文案走插件自己的 locale 命名空间 `sessionTrash`。与现有四项在结构、尺寸、图标风格、快捷键位（无）上完全一致。
- **FR-1.3** 选择该项后先关闭菜单，再打开确认对话框（菜单随行卸载，因此对话框必须注册在 `shell.overlay`）。
- **FR-1.4** 「安静」的会话（可删、未被宿主持有、无进行中的工作、未在运行）**跳过对话框**：预检通过即直接删除，只留可撤销的 Toast。需要同意的会话（运行中 / 有定时任务投递到它 / 宿主仍持有）才打开对话框，把「强制删除」这个后果摆在用户眼前。判定复用 `isQuickDelete(plan)`，与 FR-2.3 的文案规则同源。
- **FR-1.5** 快捷路径被宿主拒绝时（例如恰好在这一刻开始运行），对话框带着那条拒绝原因打开，用户可以当场重试——而不是弹一个失败 Toast 让用户从头再来。

### FR-2 单步确认流程（点击即进回收站）✅ 已实现

> **本节的形态由用户明确要求决定，取代了最初设计的两步确认。** 原始设计是「第一步选择 → 第二步确认后果」；用户要求「把下一步换成删除，点删除直接进回收站」。安全性因此改为依靠「回收站可恢复 + 事前把后果讲清楚」，而不是让用户点两次。

- **FR-2.1** 菜单「删除会话」打开对话框，对话框本身承担全部确认职责：列出将删除的会话（标题、`运行中` / `已归档` / `已置顶` 标签、原因标签）、回收站路径、以及「之后可随时在那里恢复」。
- **FR-2.2** 对话框的主按钮**一次点击即完成删除**。不存在「下一步」：弹窗的职责就是确认删除本身，点击即删除。
- **FR-2.3** 主按钮文案随状态变化（**文案是契约，不是措辞**）：
  - 无进行中的工作 → **删除**；
  - 存在进行中的工作、存在投递到该会话的定时任务、或会话仍被运行时占用 → **强制删除**。

  按钮上方必须**按真实原因分层说明**，而不是把所有需要同意的会话都说成「有工作在进行」：

  | 真实原因 | 说明文案要点 |
  |---|---|
  | 有正在进行的工作 | 「会先停止这些工作，被停止的工作不会自动继续」 |
  | 有定时任务会投递到选中的会话 | 「此刻并没有在跑；删除会连带删掉这些定时任务，它们不会自动恢复」 |
  | 会话只是仍被运行时持有 | 「没有正在运行的工作；会先把它从运行时释放，不会停止任何工作」 |
  | 工作状态无法确认 | 「会先尝试停止它们可能仍在进行的工作」 |

  行内**原因标签**同样按真实原因取值，四选一（不是叠加）：`仍有进行中的工作` / `N 个定时任务会投递到此会话` / `运行时仍持有` / `无法确认该会话是否仍有正在进行的工作`。判据由 `consentTag(plan)` 给出（`activityKnown === false` → 无法确认；有非 `schedule` 的 activity 家族 → 有工作；有 `schedule` 家族 → 定时任务；否则 `resident` → 运行时仍持有）。

  **定时任务家族（`kind: "schedule"`）不是「正在进行的工作」**：宿主 `workspace/session-activity` 的 schedule 提供方只判断「有一条 status 为 active 的定时任务指向该会话」，与此刻是否在跑无关；把它算进「工作进行中」正是已结束的对话仍被标成「仍有进行中的工作」的原因。

  按钮命名的是**动作**（删除），不是文件的去向（回收站）。去向由对话框描述与结果提示负责说明——这既符合用户的预期，也是本需求被明确要求两次的点，因此由测试固定（见 `TEST-PLAN.md` 用例 18/19）。
- **FR-2.4** 未选中任何会话时主按钮禁用，避免空提交。
- **FR-2.5** 执行期间按钮禁用，避免重复提交；失败原因（按条目的 `code`/`message`）汇总显示，而不是只给一个数量。
- **FR-2.6** **删除必须成功，不能把用户卡死。** 用户同意「停止并删除」之后，宿主的责任是把删除做完，而不是因为运行时还持有该会话就拒绝。释放会话是宿主的职责，不是用户的操作要求：

  | 步骤 | 由谁做 | 说明 |
  |---|---|---|
  | 1. 释放视图引用 | 客户端 | 若目标包含当前打开的会话，先切到另一个幸存会话；没有幸存者则释放主选区（`uiWorkspace.openSession` / `clearMain`），并关闭本客户端为这些会话开的 scope |
  | 2. 停止进行中的工作 | 宿主 | 复用 `workspaceRegistry.stopSessionActivity`（归档流程的同一条接缝）。**注意这条接缝对定时任务是终局的**：dsh-schedule 在 `workspace/session-stop` 上把指向该会话的定时任务行**从存储里删掉**，所以「同意停止」= 这些定时任务不会自动恢复——这一点必须由对话框说清楚（见 FR-2.3） |
  | 3. 归档以促成释放 | 宿主 | 复用 DSH 自己的归档：它门禁所有唤醒，并让持有主引用的客户端放手，从而让运行时 dispose 会话、关闭写句柄 |
  | 4. 等待释放 | 宿主 | 有界（≤15 秒），且发生在会话已被停止与归档之后；已同意强制的只探 250ms |
  | 5. 强制完成 | 宿主 | 若仍未释放，**先把会话从运行时拿下**（活会话注册表自带的 `detach()` 释放器），等最后一次 drain 后再移动文件；释放器不可用才退化为「仍然移动 + 保留归档」，并在 manifest、审计日志与提示条中记录 `forced: true` |
  | 6. 回滚归档 | 宿主 | 若移动最终失败，把第 3 步写入的归档撤销，绝不让用户看到一个自己没归档却被隐藏的会话 |
  | 7. 记账收尾 | 宿主 | 释放成功 → 移除归档 id（行彻底消失）；运行时仍持有 → **保留**归档 id 以隐藏残留行，并返回 `residue: true`；两种情况都**不 detach**（见 FR-2.8） |

  **禁止的行为**（这正是用户报告的缺陷）：先停止用户的工作，然后因为无法释放而拒绝删除。停止工作与删除必须同生共死。
- **FR-2.7** 未经同意（未点带停止语义的按钮）时，拒绝路径必须**零副作用**：不停止任何工作、不写归档、不移动任何文件。

- **FR-2.8 删除后不得留下可见的残留行。** DSH 的会话列表把**驻留内存**的会话也算进去，而全产品没有公开的 dispose-by-id 接口，因此被删除的会话可能「文件已进回收站、但侧栏仍有一行」。插件必须让这一行不可见、可解释、且可自行消失：

  | 规则 | 原因 |
  |---|---|
  | **绝不把会话从工作区里 detach** | 侧栏「未分组」的定义就是「列表里有、但没有任何工作区认领的会话」；detach 恰好把残留行推进那个桶（这正是用户报告的「删除后出现在未分组里」）。惰性 id 无害，且保留归属让恢复能回到原工作区 |
  | **只有运行时仍持有时才保持归档** | 默认过滤器下 `sessionVisible` 返回 `!archived.has(id)`，归档是唯一能隐藏一行的状态。但会话能被释放时（正常删除、或强制删除时插件主动调用 `ctx.sessions.store.get(id).detach()`），宿主不再列出它、行彻底消失，此时**必须** unarchive，否则已删除的会话会留在「显示已归档」里 |
  | **列表里无文件的会话显示为「残留」** | 宿主 `plan` 对它返回 `not-found`；把它标成「不可删除」会让用户以为自己刚做的删除失败了，且会被计入「无法删除」的计数 |
  | **批量列表不列出已删除/已归档的行** | 回收站里的会话，其目录已被移走，但运行时仍持有该行——侧栏看不见它，批量删除列表却列着它，旁边还挂着「已删除」徽标和一个复选框。这等于承诺一次早已发生过的删除，还让「全选」把用户从未在侧栏见过的行一并扫进去。判定由宿主预检给出（见 FR-3.3a） |
  | **无文件的会话可以被选中并清出列表** | 「能不能删」是用户的决定（见 FR-2.9）。这样的行没有文件可移动，宿主就把它**清掉**：停止工作（需同意）、释放运行时、归档隐藏、`emit "api-session/removed"`，并在审计里记 `delete:cleared`。UI 文案必须说「只从列表移除」，不能谎称「已移入回收站」 |
  | **提示条说明残留何时消失** | 残留随进程结束而消失：重启 DSH 后彻底不见。这是可验证、可预期的，不是含糊的「稍后」 |
  | **删除「当前正在看的会话」必须先说明后果** | 对话框给该行加「当前会话」标签，并写明「删除会立刻结束这段对话」；插件随后自动切走视图，用户不需要自己先切换 |

- **FR-2.9 「能不能删」由用户决定，宿主只回答结果。** 这是用户的明确要求（原话：「所有的删除应该由我决定能不能删，而不是直接把这个决定给定死」）。因此：

  | 规则 | 原因 |
  |---|---|
  | **列表里的每一行都可勾选**，包括 `not-found`、`unsafe-location`、`invalid-session-id` 的行 | 用 `disabled` 把选项拿走，等于插件替用户做了决定；用户看到的是「无法选择」，而不是原因 |
  | **禁用条件只剩「一个都没选」** | `canAdvance` 只判断「有选中项」；提交后由宿主逐项返回结果与原因 |
  | **提交携带全部选中项**，不做客户端过滤 | 客户端的 `deletable` 只用于**显示标签**，不再是门禁；真正的判断在宿主，且逐项可解释 |
  | **仍然拒绝的只有两件事**：无法安全确认的路径（`unsafe-location`、`invalid-session-id`）与未经同意的停止（`session-active`、`session-live`） | 前者是「不能删别人的文件」的安全边界，后者是「不能悄悄停掉你的工作」的同意边界；两者都会把 `code` / `message` 原样返回给用户，而不是灰掉按钮 |

### FR-3 批量删除 ✅ 已实现

- **FR-3.1** 在 `sidebar.workspaces.session.menu.item` 新增「批量删除会话…」行，`order = 600`，带分隔线，从任意会话行均可进入。
- **FR-3.2** 批量对话框列出候选会话：默认**全不选**，提供「全选 / 取消选择」、标题与会话 id 搜索、已选数量提示。**全选**作用于当前搜索结果（所见即所选）。
- **FR-3.3** 候选集合排除空白会话（未产生首条消息）与子代理（subagent）会话——它们不是用户意图删除的「对话」。
- **FR-3.3a** 批量列表**不列出用户已经无法再删的行**：宿主预检判定为**已归档**（`archived`）或**已删除**（文件已不在、只剩残留行，`exists: false` / `code: "not-found"`）的行，都不进批量列表。判定依据是宿主预检的结果，不是客户端的猜测——客户端看不到归档集合，只有宿主能区分「残留行」与「只是被隐藏的会话」。**单会话对话框不受此限**：用户点名问的那一行仍然显示（见 FR-2.9 与「列表里无文件的会话显示为「已删除」」）。
- **FR-3.4** 候选会话**全部可勾选**（见 FR-2.9）：无法定位目录的行只标注原因（`目录无法确认`），不灰显、不挡勾选；对话框下方说明这些行的删除会被拒绝，其余行照常删除。
- **FR-3.5** 批量提交后按会话逐个返回结果，部分失败不影响其余成功项，UI 如实报告失败数量与去重后的原因（最多 5 条）。
- **FR-3.6** 单次**变更**上限可配置（`maxBatch`，默认 100，硬上限 1000），在请求层统一校验；`purge` 的 `["*"]` 哨兵豁免（它命名的是回收站自身内容）。
- **FR-3.7** 客户端按 `maxBatch` **切批**发送预检与删除：用户在对话框里选多少，就删多少。`maxBatch` 是防滥用护栏，不是用户体验的上限——绝不出现「选了 120 个 → 整次预检 400 → 对话框空着」这种死胡同。某一批被请求层拒绝时停在那一批，已到达的裁决原样保留（已进回收站的会话仍可撤销）。
- **FR-3.8** 预检（`plan`）的 id 上限单独放宽到 `max(配置 maxBatch, 500)`：它是只读动作，且客户端已经切批，放宽后连「选了几百个」这种极端情形也能正确预检。
- **FR-3.9** 批量列表按**工作区分区**展示，每个分区可**折叠 / 展开**：分区维度取会话自己的工作目录（`cwd`，即侧边栏已经使用的那个维度），没有工作区的会话归入「未分组」一个分区；分区按会话出现的先后排列，不做字母序重排。分区头显示目录名、完整路径与数量，并带一个**组复选框**（勾上＝选中该分区当前可见的全部会话；部分选中时显示「已选 N/M」而不是假装全选或全不选）。分区折叠状态是对话框状态的一部分（重新渲染不丢），提供「全部展开 / 全部折叠」。**搜索时自动展开**仍有命中的分区——看不见的命中不算命中。
- **FR-3.10** 分区是**呈现层**的划分，不改变任何删除语义：选中集合、请求体、逐项结果与原因都与分区无关；单会话对话框不分区。

### FR-4 回收站与恢复 ✅ 已实现

- **FR-4.1** 删除 = 把会话目录**移动**到回收站，不 unlink。回收站默认位于 `<dshHome>/session-trash`（可配置）。
- **FR-4.2** 每个回收站条目携带 manifest，记录：`trashId`、`sessionId`、原始绝对路径、工作区路径、标题、删除时间、删除前的归档/置顶状态、文件清单与总字节数、执行者标签。
- **FR-4.3** 「恢复」把条目放回**原始绝对路径**，字节级一致。
- **FR-4.4** 若原始路径已被占用（例如同名会话被重新创建），恢复**拒绝并保留回收站条目**，绝不覆盖、绝不合并。
- **FR-4.5** 删除成功后弹出可撤销提示（Toast），「撤销」即恢复；另提供「查看回收站」直达侧栏回收站面板。
- **FR-4.6** 侧栏的「更多」菜单里新增「回收站」一行（`sidebar.panellist.actions` 槽位，id = `session-trash.more`，order = −20；宿主按 `order` 升序渲染菜单行，内置两行为 0），并保留主面板页（`main` 槽位，key = `session-trash`）。侧栏不再常驻「回收站」行。
- **FR-4.7** 面板提供：条目列表（标题、删除时间、大小、原工作区、超期标记）、多选、恢复选中、彻底删除选中、刷新、操作日志折叠区、空状态。选中的条目多于单次请求能带的数量时，**按 `maxBatch` 分批提交**（与删除路径同一套逻辑），不整次撞上 `batch-too-large`。
- **FR-4.8** 损坏条目单独归类提示，数量可见，不混入可恢复列表：manifest 损坏（`corrupt`）、payload 缺失（`failed`）、**无 manifest 的孤儿目录**（`orphan`，例如在 `mkdir` 与写 manifest 之间崩溃）、以及 **manifest 能解析但状态是本版本不认识的**（`unknown-state`，例如另一个版本写的条目）。孤儿与未知状态过去的字节既看不见也删不掉，现在会在列表里报告并可被彻底删除。
- **FR-4.9** 恢复不只是把文件搬回去，还要把会话**挂回运行时**：文件与记账就位之后、通知客户端之前，调用宿主的 `sessionController.resolveAgent(sessionId)` 触发 `resolve → resume`（`#reviveSession`，超时 `reviveTimeoutMs` 默认 8000ms）。仍驻留的会话记 `already-live`，不重复 resume；宿主没有该接口记 `no-resume-api`。复活失败**不**把恢复判成失败（文件与记账已经就位），但必须在结果行里如实反映：`revived: false` 加 `reviveCode`（`resume-failed` / `no-resume-api`）与 `reviveMessage`，界面据此提示「文件已恢复，但没有重新挂载到运行时（原因）：重启 DSH 后即可继续对话」。
- **FR-4.10** 客户端在恢复后**丢弃陈旧实例**：删除时留下的会话实例带着 `removed` 标记（`handleRemoved()` 只打标记、不销毁，`handleSessionAdded()` 也不清它），恢复后不得复用——`removed === true` 的走 `sessions.retireScope(id, scope)`，否则走 `sessions.manager.drop(id, instance)`，由下一次打开重新懒建；并且当被恢复的会话正是删除前 main view 上那一个时，恢复后重新打开它。

### FR-5 彻底删除（不可恢复）✅ 已实现

- **FR-5.1** 彻底删除必须显式确认：UI 侧的确认就是「确认彻底删除」按钮本身（用户明确要求去掉多一次的勾选），客户端把这次点击翻译成请求体的 `acknowledge: true`；宿主侧仍要求该字段，缺失即 428 拒绝。
- **FR-5.2** 支持按条目彻底删除，以及清空整个回收站（`trashIds: ["*"]`，同样需要 `acknowledge`）。
- **FR-5.3** 彻底删除是**唯一**的不可逆操作，且只能从回收站发起，永远不会被删除流程自动触发。
- **FR-5.4** 面板提供「清空回收站」，走同一条 `acknowledge` 门槛（内部用 `trashIds: ["*"]` 哨兵，宿主在确认之后才展开）。面板内的**彻底删除**是唯一不可逆的操作，与菜单里的**删除**（进回收站、可恢复）语义清楚区分；同意由点击确认按钮表达，不再另设勾选。

### FR-6 保留期（报告式，不自动销毁）✅ 已实现（按设计）

- **FR-6.1** 可配置 `retentionDays`（默认 30）。超过窗口的条目在面板上标记「已超过保留期」，并在统计里给出数量。
- **FR-6.2** **插件不会自动删除到期条目。** 这是刻意的设计选择：静默销毁用户数据不可接受。自动清理若将来需要，应作为显式的、默认关闭的配置项，并在文档中显著声明。
- **FR-6.3** `retentionDays: 0` 完全关闭超期报告。

### FR-7 审计日志 ✅ 已实现

- **FR-7.1** 所有变更（`trash` / `restore` / `restore-revive` / `purge`）与所有拒绝（`delete` + `refused` + 原因码）写入 `<trashRoot>/logs/trash-<YYYY-MM-DD>.ndjson`，每行一条 JSON，追加写。`restore-revive` 记录 `outcome`（`ok` / `failed`）与原因码（`resumed` / `already-live` / `no-resume-api` / `resume-failed`），失败时的 `message` 也一并落盘。
- **FR-7.2** 每条记录包含：`ts`、`tsIso`、`pid`、`host`（主机名哈希，不落明文）、`op`、`outcome`、`sessionId`、`trashId`、`originalPath`、字节数、`actor`。
- **FR-7.3** 日志写失败只告警，不让业务操作失败（日志是证据，不是前提）。
- **FR-7.4** 面板内可查看最近 50 条；`GET /session-trash/log?limit=N` 可取更多。

### FR-8 兼容性与无侵入 ✅ 已实现

- **FR-8.1** 不修改任何 DSH 源码或既有配置文件内容（仅由用户/插件管理器追加自己的 bundle 行）。
- **FR-8.2** 不改动原有四项菜单、归档语义、排序、置顶、分叉行为。
- **FR-8.3** 客户端 `inject` 导出为空数组，所需服务全部在 `apply` 内用 `ctx.inject` 响应式获取，且**只通过注入作用域**（`scope.<service>`）访问服务属性。Cordis 会门禁未声明服务的属性访问并抛错，而 DSH 的启动审计要求每个 entry 都 ACTIVE——所以「不在顶层读 `ctx.locale`」是硬要求，不是风格问题（详见 `ARCHITECTURE.md` §1.1，该规则由客户端测试的 Proxy 假上下文强制）。
- **FR-8.4** 宿主端只注册**一条**前缀路由 `/session-trash`，不占用其他插件的路径。
- **FR-8.5** 零运行时依赖：宿主端只用 Node 内置模块，浏览器端只用平台冻结模块表（`react`、
  `@deepseek-ai/dsh-client-ui-primitives`、`@deepseek-ai/dsh-client-store`）。安装无需联网解析依赖。

## 3. 非功能需求

### NFR-1 数据安全（最高优先级）

| 规则 | 实现方式 |
|---|---|
| 删除前绝不移动可能仍被写入的目录 | 会话仍在内存（`ctx.get("sessions")` 可查到）时**拒绝**；只有调用方明确同意后才等待其离开内存，超时仍拒绝 |
| 不越过文件系统边界 | 会话 id 必须匹配 `^session-[A-Za-z0-9._-]{1,120}$`；`trashId` 必须匹配 `^t-\d{8}T\d{6}Z-[0-9a-f]{8}$`；所有目标路径做 realpath 包含性校验，越界返回专门的 `unsafe-location` 拒绝码 |
| 不跟随符号链接 | 源目录与候选目录都用 `lstat` 判定，symlink 一律拒绝 |
| 不覆盖任何已存在目录 | 回收站落点要求不存在；恢复要求原始路径不存在 |
| 崩溃可恢复 | 先写 `state: "moving"` 的 manifest，再 `rename(2)` 原子移动，最后改写为 `trashed` + 文件清单；跨文件系统时先复制到 `payload.tmp` 再 rename 就位 |
| 拒绝即无副作用 | 所有守卫在**任何**文件操作之前求值；被拒绝的请求不创建回收站目录、不改 manifest；自愈只在内存中进行，`list()`（GET）与被拒绝的 `restore()` **都不写盘** |
| 移动成功即不再抛错 | 引入**提交点**：`rename` 之后的一切失败（跨设备时的源目录清理、文件清点、manifest 收尾）只记警告字段与审计，绝不抛出——否则调用方的回滚会删掉唯一完整副本 |
| 不可逆操作显式授权 | 彻底删除要求 `acknowledge: true`；UI 的「确认彻底删除」按钮就是这次授权 |

### NFR-2 性能

- 删除单个会话：1 次 `rename` + 1 次目录清点（会话目录通常 2–3 个文件）。实测批量 100 个在毫秒级。
- 预检（`plan`）按 `PLAN_CONCURRENCY = 4` 并发逐项检查，结果保持输入顺序；默认**不**统计目录字节数（`bytes: 0`，需要时传 `sizes: true`）。实测 17 个会话 39 ms。
- 列表：读取 `items/*/manifest.json`（无持久化索引，因此不存在索引与实体不一致的可能）。O(条目数) 次小文件读。
- 所有变更操作串行化（`SerialQueue`），避免并发写坏 manifest。
- 全程不阻塞 DSH 主流程；路由处理在请求内完成，不做轮询、不注册定时器。

### NFR-3 可审计与合规

- 删除、恢复、彻底删除、拒绝四类事件全部留痕，含时间、主体（`actor`）、对象、结果、原因码。
- 主机名只以 SHA-256 前 12 位十六进制记录，避免日志本身泄漏机器标识。
- 回收站默认保留 30 天报告期，为误删提供窗口；恢复是字节级还原。
- 本插件不采集、不外发任何遥测。

### NFR-4 可维护性

- 宿主端按职责拆分为 `encode` / `locate` / `trash-store` / `service` / `routes` / `access`，纯函数与 IO 分离，全部可用 `node --test` 直接测试。
- 零构建步骤：`lib/**` 即源码，没有编译产物与源码不同步的风险。
- 140 个自动化测试（137 个必测 + 3 个真实 React 渲染检查）；关键编码函数以「本机真实目录名」作为回归锚点；对抗性复核发现的缺陷每个都有对应回归测试。

### NFR-5 可访问性

- 菜单行、图标按钮、复选框均带 `aria-label` 或可见文本。
- 图标按钮带 `Tooltip` 文案；危险按钮有文字而非仅图标。
- 错误信息使用 `role="alert"`；对话框具备标题与描述。

## 4. 范围外（明确不做）

| 项 | 原因 |
|---|---|
| 自动清理到期条目 | 静默销毁用户数据不可接受（见 FR-6.2） |
| 设置页图形化配置 | 需要引入 `@deepseek-ai/schemastery` 依赖并依赖设置页生成机制；本版以 `cordis.patch.yml` 的 `config:` 块配置，保持零依赖 |
| 删除工作区 | DSH 已内置「删除工作区」（会话归入未分组），不属于本插件职责 |
| 删除进行中的会话而不停止工作 | 会导致运行中的 Agent 写入已删除目录；一律拒绝并要求显式停止 |
| 绕过 `acknowledge` 的批量彻底删除 API | 安全门槛不接受编程式绕过 |
| 会话内容的加密粉碎（secure erase） | 现代 SSD / APFS 上不可靠，做「合规的粉碎」承诺是虚假保证；本插件只保证文件被移除 |

## 6. 与现有系统的边界

插件**只通过公开接缝**与 DSH 交互，不讀写 DSH 内部私有字段（唯一例外见下）：

| 接缝 | 用途 | 稳定性 |
|---|---|---|
| `ctx.sessionPersistence.stat()` / `.root` / `.locate()` | 定位会话目录 | `stat` 是契约方法；`root`、`locate` 是 JSONL 后端实现上的方法，因此实现为**可选优先**并配有纯计算的回退层 |
| `ctx.workspaceRegistry`（`archivedSessionIds` / `pinnedSessionIds` / `list()` / `Entity.detachSession` / `unarchiveSession` / `unpinSession` / `stopSessionActivity`） | 清理 DSH 自身的持久化记账 | 公开服务 |
| `ctx.waterfall("workspace/session-activity")` / `ctx.parallel("workspace/session-stop")` | 判断与停止进行中的工作 | 归档流程使用的同一接缝 |
| `ctx.webServer.register({kind:"prefix", path, handler})` | HTTP 传输 | 公开服务，插件唯一可行的传输方式（Remote 命名空间是构建期装配的，外部插件无法贡献） |
| `ctx.slots.inject()` / `ctx.slots.register()` | 客户端 UI 注入 | 公开槽位系统 |
| `ctx.locale.register()` / `.bind()` | 文案 | 公开服务 |
| `ctx.emit("api-session/removed" / "added")` | 通知其他客户端刷新列表 | 会话控制器自身使用的事件 |

**唯一的私有字段读取**是 `trash-store` 通过 `ctx.get("sessionPersistence")` 拿到的实例上的 `root` 与 `locate()`。两者都做了存在性与形状判断，缺失时自动降级到纯计算的路径推导（已按后端源码逐字节复刻并用真实目录名做回归测试）。
